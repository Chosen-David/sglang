## S1 封面：速度卖点三支柱（开场 2 分钟）

**口播**：
> 各位老师好。今天汇报的工作是 TLI——一个两级 training-free 稀疏注意力索引。全部实验与优化主线已收官，这页是终局数据总览。
> 卖点定位是**速度**：同精度梯队下，三个层面的加速——kernel 级两级选择相对 dense 打分 1.3 到 5.1 倍（32K 到 128K 梯度，越长越快）；30B 单请求 64K 端到端 1.285 倍领先 dense，这是稀疏理论流量收益第一次在我们系统里净兑现；8B 稳态批量形态 prefill 733.9→183.4 秒（4 倍）、decode 65→33.5 毫秒（1.94 倍）。
> 质量侧一句话带过：RULER 官方口径对 Quest 领先随长度超线性扩大，最大 +8.49 分；对同门 TIA 的代价集中在两个可精确定位的任务族。所有结果含负结果都在同机同口径下诚实报告——这也是方法论贡献的一部分。

**预期提问**：
- *Q：8B prefill 4.00× 的口径？* → 稳态批量（bs16 × S=30K × n=256，差分法 P1D1P2D2 交替消除漂移）；对 dense 同臂是 1.60×，4.00× 是相对 TLI 自身旧基线的优化链累计。表上打了 \* 号，答辩时主动说清。
- *Q：为什么 32K 档 0.77× 是负收益还敢报？* → 双口径诚实报告是本项目铁律；短上下文固定开销未被收益覆盖，机制清楚（下页细说）。

## S2 RULER 终表（3 分钟）

**口播**：
> 质量主表用 RULER 官方预生成数据集，3 长度 × 11 任务 × 每任务 100 条，四方法完全同一 monkeypatch 基座。
> 三个观察：**第一**，TLI 对 Quest 的领先从 4K 的 +2.91 到 16K 的 +8.49，超线性扩大。根因是表示差异：Quest 用 page-min **下界**近似会漏选真实高分页，长上下文干扰项超线性增多时崩塌——16K 档 Quest 的 multikey_3 只有 21 分、cwe 29.5；TLI 的 minmax **上界**粗筛保证无漏选，同任务保持 52 和 54.9。**第二**，TLI 相对 TIA 的代价可以精确定位：AVG 差 −0.81 到 −5.86，但全部集中在 multikey_3 和 cwe 两个任务族——前者是 K1 块配额被超多干扰 key 稀释，后者是 far/near 分区挤占逐词召回预算；其余 9 个任务零差或反超，fwe 上 TLI 还超过 FullKV，是稀疏降噪的正向例。**第三**，绝对值解读必须以同长度 FullKV 为基线——聚合列举类任务 FullKV 自己也在退化，同长度上的 gap 才是稀疏效应。

**预期提问**：
- *Q：16K −5.86 会不会太大？* → LongBench 多跳口径下 TLI 与 TIA 差小于 0.3——单跳口径放大代价、多跳口径放大小收益，两表互补并报，用户按任务形态选。
- *Q：为什么不和 SnapKV/H2O 比？* → 对齐口径选了 training-free 且有官方 kernel 可摘的三家（Quest/DSA/官方 kernel 对比在 kernel 页）；TIA 是同门内部消融基准。

## S3 e2e 终值（3 分钟）

**口播**：
> 端到端双口径，同机同臂。核心行是 30B 单请求 64K：dense 21.06 秒，TLI 终版 16.39 秒，1.285 倍——从旧版的 1.005× 翻正，意味着稀疏理论流量收益第一次在 e2e 净兑现。8B 稳态 decode 33.5 毫秒已经反超 dense 的 40.4 毫秒。
> 两个诚实项：32K 档 0.77×，短上下文选择固定开销未被收益覆盖，如实报；TP2 bs16 64K 为 0.92×（差 8%），归因是 launch-bound——16 个请求逐请求 Python 循环 × 36 层 × 数十个小 op，GPU 利用率名义 100% 但显存带宽利用率只有 10-11%，说明是 launch 串行不是带宽瓶颈。修复方向是跨请求批量化 forward_extend，decode 侧同款方案已验证 3.8 倍，列为 future work，不阻塞论文。

**预期提问**：
- *Q：launch-bound 的证据链？* → 三条：py-spy 主线程 100% CPU、循环体单 op 微基准外推仅 0.5 秒、GPU util 与带宽 util 的背离。
- *Q：批量化为什么不现在做？* → 是明确路径而非未解难题（M4 已验证 decode 侧），工程量在 forward_extend 路径重构；论文按诚实归因+future work 处理。

## S4 优化链与方法论（3 分钟）

**口播**：
> #65 优化链按 commit 粒度全部双层验证。①prefill select 三连：早期行向量化把 5K 次 launch 收成单 op、fast_path 旁路、dual kernel bf16+pad 直出，合成口径 2.06 倍且 jaccard 0.996 逐位不变。②decode 侧 DeepSelect topk 接入 L1 和 far 池，near 池保留 torch——因为 4bit 量化 tie 组巨大，集合 jaccard 只有 0.72，这是负结果。③GPU 同步消除：3 处 .item()/.any() host 同步在生产形态造成约 10 万次队列排空，合成 bench 完全测不出，消除后 8B prefill 再降 6.7%。
> 这条是方法论贡献：逐 kernel microbench 与生产 e2e 存在系统性口径差，即 host-GPU 流水线效应，同步消除类优化必须在 e2e 层验证。④动态测层 gate 三任务代价 AVG −0.17，远优于静态版 −4.8~−5.9。⑤负结果资产全部有编号有脚本：H 卡 TC 化、TMA、聚类代表、near DS、gate 判据五项 No-Go。

**预期提问**：
- *Q：为什么这么多 No-Go？* → H20 的 Tensor Core 吞吐只有 H100 的 15%，ρ 实验证明打分 GEMV 在 d'=32 形态下是带宽受限——No-Go 是设计约束推导出来的，不是试错出来的；这些负结果恰好支撑了「消除中间物化+合并 launch」的 kernel 设计主线。

## 高危问题预案（从防御清单精选，答辩前必背）

1. **「two-level 和 HISA 有什么区别？」** → 结构同构我们不争；增量在表示（上界 vs 下界）+ 预算组织（分区 vs 全池）+ 质量代价定位的系统刻画，每条都有实验编号。
2. **「三方 kernel 对比你们最快吗？」** → **不是，绝不这么说**。Quest 0.107ms 最快，TLI 0.787ms 不占优，如实报告；优势在算法结构——每 token 索引 MAC ≈258 是 DSA 的 1/32、存储 3 倍降、质量 +2.2，131K 下三家都远离 HBM bound，排名反映实现成熟度，kernel 化是兑现路径。
3. **「8B 有 bug 30B 才崩，说明什么？」** → 早期行非因果泄漏 8B 耐受未崩、30B 崩，已根因修复（commit 2d6b0e4be）；反过来证明 30B 是更严格的正确性试金石，如实报告。
4. **「32B 上还成立吗？」** → A 机制存在但强度递减（如实报告）、D' 更强（41/64 层 precision 0.993）、far 双峰复现——泛化结论分层给，不打包票。
5. **「上界粗筛的理论保证？」** → 无漏选：块上界是该块对任意 token 分数的上界，top-K1 块必然包含全局 top token 所在块；对比 Quest 下界无此保证（16K 崩塌根因）。
