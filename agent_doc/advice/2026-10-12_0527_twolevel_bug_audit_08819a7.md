## TL-E127-DEFERRED-ERROR-095

### 可达机制

`eager_decoding.py:18-25` 明确规定三类契约错误先写设备级 `_ERR_FLAG`，生成结束由 `eager_decoding_check_errors()` 一次读回，仍应“显式 raise、整次生成作废”。实际行为是：

1. Triton expand kernel 在空行、超 `W`、非法 `cu` 时写 code 1/2/3；attention kernel 把 `cnt` 截到 `W`，空行则因 `l==0` 产出零向量（`:120-139,151-187`）。
2. Torch gather fallback 同样只 `flag.copy_()`，随后固定 `topk(W_upper)` 并继续算 attention（`:428-475`）。
3. 唯一读取者是 `eager_decoding_check_errors()`（`:38-60`）；全仓调用只出现在 `exp/bench/test_e127_gates.py` 与 `exp/bench/e127_stage_bench.py`。
4. LongBench 在完成 decode 后直接形成 `record` 并写 JSONL；RULER 直接写 generation；lm-eval 在 `simple_evaluate()` 后保存结果。三条生产链均没有 import 或调用错误读取者。

### 触发条件、实际与预期

| 项目 | 内容 |
|---|---|
| 触发条件 | `TLI_E127_FAST=1`、长序列进入 gather，且任一行全 False、真实选择数超过 `TLI_E127_W_UPPER`，或 `cu_seqlens_k != [0,S]`。默认 env=0、短序列 dense 回退不受影响。 |
| 实际行为 | flag 留在模块全局设备缓冲；当前请求继续生成并可能写出结果。超上界时只消费前 `W` 个位置；空行 Triton 路径给出零输出。生产入口永远不读 flag。 |
| 预期行为 | 在请求/文件结果发布前恰好调用一次检查器；有错误则整次请求失败且不得留下完成外观产物，随后按请求作用域清理 flag。 |

### 已跑数据影响边界

- E127 自带门禁在每个异常用例后显式调用检查器，且正式 microbenchmark 使用合法 mask；本发现不否定其正常输入 allclose，也不使已提交的 synthetic 计时失效。
- 仓内正式 run 脚本没有开启 `TLI_E127_FAST=1`；默认路径和当前 DeepSeek `method=none` 重跑不受影响。只有实际打开 E127 快路径的 Qwen/Llama/TLI 生成受影响。
- 没有发现错误 flag 日志或已知超界样本，不能宣称历史结果已经错算；风险是异常输入会被静默发布，而不是正常输入必错。

纯算术反例无需 GPU：令 `S=16384,W=2048`、mask 全 True、所有 `q·k=0`，并令 `v[:W]=0,v[W:]=1`。完整 attention 是全序列均值 `0.875`；Triton expand 按 token 升序只保存前 `W` 个索引，attention 又把计数截到 `W`，得到 `0.0` 并仅留下 code 2。该反例证明“flag 未消费”可以对应真实语义差异，但它不是 GPU 执行实测。

### 建议修复与重测

1. 在 LongBench、RULER、lm-eval 的真实请求边界接入统一 `try/finally` 生命周期：请求开始清旧 flag，生成结束、任何落盘/提交指针之前检查；失败时不得写完成回执或正式 JSONL。
2. 不应由每个 benchmark 手工维护同一约定。优先在 patch/model generation wrapper 建立请求级 API，避免新增入口再次漏接；并处理同进程并发请求的设备全局 flag 隔离。
3. 加生产入口级门禁，不只直接调用算子：分别注入空 mask、`W_upper` 过小和非法 `cu`，断言入口非零退出、正式输出不存在；随后合法请求不得继承旧 flag。

## TL-DSV2-CAP-PROVENANCE-096

### 修复链中的残余缺口

`TL-DSV2-CONTEXT-CAP-093` 的能力误写已经改正：注册表保留 protocol `31500`，把当前 `16384` 明确命名为 `restricted_context_treatment`，启动门禁也打印 divergence。这一部分应保留。

但“结果文件须标注 16K 受限上下文口径”的落盘闭包没有实现：

- `enforce_context_capability_gate()` 返回包含 `experiment_input_cap` 的字典（`context_capability_gate.py:162-168`），`pred.py:518-520` 未接收返回值。
- 每行 JSONL 只记录数据集原字段 `length`，未记录本次 `max_length`、模板后实际输入 token 数或是否截断（`pred.py:369-388`）。
- 文件名只由 dataset、稀疏 method 和时间标签组成，cap 不在身份中（`:610-632`）。
- sidecar 仅在 `args.method == "tli"` 时写（`:649-653`）；当前 DeepSeek fullkv 的 `method=none` 根本没有 sidecar。
- 即使未来 DeepSeek TLI 路线使用 sidecar，`sparse_attn/info.py` 的 treatment manifest 也不消费 `model2maxlen`。测试 `T21` 还把这种解耦固定成绿门禁（`test_dsv2_093_094_fix.py:414-420`）。

因此，同一 task/method/时间标签若先后用 16K 与 31.5K 运行，路径和记录结构完全相同；后跑可覆盖前跑，或在汇总阶段被当成同一 treatment。启动 stdout 能说明当时发生了什么，但 stdout 不是结果产物的强绑定元数据。

### 已跑数据影响边界

- 仓内 advice 记录显示，修复后的 `.24` DeepSeek 16K 重跑已有多项完成/在跑，旧的 5 个非 chat 结果与新的 11 个 chat 重跑准备合并。两批在人工调度记录中都被说明为 16K，因此**没有证据表明这次合并本身混入了 31.5K**。
- 时间标签 `023927`、`043751` 和外部任务报告目前提供人工可追踪线索；但 JSONL 自身不能复核 cap。复制、重命名、脱离 stdout 或未来 31.5K 路线启用后，这一线索会丢失。
- 之前 `.251` 的 16 任务被后续实查为 0 样本，本项不改变该结论。影响重点是已开始产出的 `.24` 受限 treatment 结果及未来聚合纪律。

### 建议修复与重测

1. 给所有方法（包括 `none/fullkv`）写不可分离的 run manifest/sidecar，至少绑定：模型与配置 SHA、producer SHA、protocol cap、effective cap、cap 类型/理由、chat-template 后每样本实际输入 token 数、截断标记、max_new_tokens、数据指纹和结果 SHA。
2. cap 或其 canonical manifest hash 进入输出身份；同路径已有不同 cap 时 fail closed，不覆盖。聚合器要求同一表格比较集合的 cap/treatment 字段满足冻结协议。
3. 将当前 `T21` 从“manifest 与 cap 解耦”为反向门禁：构造完全相同的 task/method/timestamp，仅改 16384↔31500，必须得到不同身份或写门拒绝；fullkv 与 TLI 都覆盖。
4. 在当前 DeepSeek 结果入表前，用外部运行日志补制带结果 SHA 的 manifest；缺日志者只作为 provenance 不完整产物，不直接进入最终论文表。

## TL-E127-PERQH-GRID-097

### 最小算术复现

调用侧统一 launch `grid=(R*G,)`（`eager_decoding.py:217`）。kernel 对每个 `pid` 先计算：

```text
j = pid % G
r = pid // G
```

共享 mask 时 `R=Hkv`，随后 `qh=r*G+j`，所以 `R*G=H` 正确。per-query-head 时 `R=H`，分支改成 `qh=r`、`kvh=r//G`，`j` 完全未使用，但 grid 没有缩回 `R`。Qwen3 `H=32,Hkv=8,G=4` 的 CPU 枚举得到：

```text
launched_programs=128
logical_output_rows=32
writers_per_qhead=[4]
duplicate_program_factor=4
```

四个 program 读取同一 `IDX/COUNT/Q/K/V`，正常确定性输入下计算目标相同并对同一 `OUT[qh]` 非原子 store。这解释了为什么现有 allclose 可以通过，却没有消除重复工作和写竞争。当前证据不足以把 PTX 同值竞争直接定性为已发生的数值错误；本项以效率/并发健壮性缺陷报告。

### 影响与修复

- E127 正式 `e127_stage_bench.py:60` 固定 `tli_per_q_head=False`，报告中的 H20 `8.29→1.52 ms`、`5.47×` 是共享 mask 路由，不受此项污染。
- `test_e127_gates.py:99-120` 覆盖 per-q-head allclose，但不统计 program 数、写竞争或该分支性能，所以不能否定此项。
- 最小修复是调用侧按 `grid=(R if per_qh else R*G,)` 派发，并让 `PER_QH` 分支把 `pid` 直接映射 qh。修复前后需在真实 GPU 上对 per-q-head 做输出差分、program/launch/显存计数和事件计时；未经实测不得声称 4× kernel 加速，因为 kernel 内访存、调度和其他阶段仍占成本。
- 建议额外覆盖 `G=1/2/4/8`、`H` 与 `Hkv` 多组、非整块 `S`、并列分数、空/满 mask 和不同 dtype；可用时运行 compute-sanitizer/racecheck，工具或架构不支持时如实记录。

## TL-E128-PARETO-098

### 当前产物中的逻辑矛盾

`pareto_analysis()` 定义质量越高、10 格稳态成本逐格不高于且至少一格更低才构成支配（`:497-503`）。实际代码只在 `q and c` 时登记关系（`:522-531`），当前生成 JSON 的五个 `dominates_point_estimate` 和 `dominated_by_point_estimate` 列表也全部为空。

但同一函数在 `not any_dom` 分支反而输出：“加入建簇+重建成本维后……簇臂在总成本维被零建簇臂（mavg/aavg）点估计支配”（`:542-550`）。这不是等价换一种成本口径：

1. 在固定“质量最大、成本最小”的 Pareto 定义下，为已有二维向量新增一个成本维只能保留或消除支配，不能创造此前不存在的支配。
2. 当前质量点估计为 `cclustersim=48.25`、`aavg=48.124`、`mavg=47.91`。因此 `mavg/aavg` 即使总成本更低，也不能在质量维支配 `cclustersim`。
3. 该摘要与同一 JSON 的空 dominance 表直接冲突；“成本在任何 decode 长度更高”可以单独陈述，但不能改写成质量-成本 Pareto 支配。

### 影响与建议

当前输入的质量、稳态成本、冷建簇成本本身可复算，本项不证明底层测量数据错误，也不自动推翻“暂不换主方法”的工程建议；它证明的是 E128 用错误的多目标术语加强了推荐论证。该 JSON 已是论文决策输入，发布前应修正。

建议返回两个明确分离的对象：`quality_steady_cost_pareto` 与 `cost_only_total_order_at_horizon`。前者必须由机器生成摘要且与 dominance 列表一致；后者显式给定 decode horizon、是否把 128 步重建率外推、真实/合成数据口径，禁止使用“Pareto 支配”。加入性质测试：给任意二维点集增加一个最小化维度后，新支配集合必须是旧集合的子集。

## TL-E128-STATEMENT-099

### 同协议补算反例

脚本只计算每个候选相对 `mavg` 的任务级配对 bootstrap，却在函数注释和 JSON `significance_note` 中写成“除 mminmax 外全部臂间质量差 CI 均含 0”。用相同 5 个任务、`B=10000, seed=42` 补算两对未被脚本计算的臂间差，得到：

```json
{
  "aavg-cavgsim": [0.110, 0.762],
  "cavgsim-cclustersim": [-0.948, -0.178]
}
```

两者都不含 0，所以“全部臂间”是当前数据上的假陈述。补算没有做多重比较校正，不能据此宣称新的最终冠军；但足以反驳现有全称命题。

另有两处内部措辞冲突：R1 先写“四候选 vs mavg 的 CI 均含 0”，同一句又正确指出 `mminmax` 的 CI `[-1.56,-0.08]` 显著更差；R6 把 E100 的含零 CI `[-0.18,+1.02]` 写成“持平”，与 `meta.statistical_discipline` 的“含 0 只能写未证明差异，不写持平/等价”相反。

建议把范围严格改为“除 mminmax 外，其余三候选 vs mavg 的 CI 含 0”，R6 改成“未证明相对 FullKV 有差异”。若需要任意臂间结论，则明确枚举并计算全部配对，说明是否做多重比较校正，不能从锚点比较外推。

| E127 run 集合 | 给 baseline 追加一个重复 run | 字典覆盖重复键后仍见 8 个键，门禁通过 |
| E127 有限性 | 把 16K normal 的配对 `step_gpu_sum_ms` 改成 NaN | `<=0` 与偏差比较均为 False，NaN 被写入结果 |

根因分别是：E125 清单只数长度、不比较预期唯一集合；质量均值从 `arm` 重算，CI 却从预存 `delta_vs_mavg` 重算，未验证 `delta == arm-mavg`；E126 只绑定 αβγ，且 `stage_ms_median` 未与 `stage_ms_samples` 联立；E127 先用字典静默去重，之后只检查键数，数值也没有 `isfinite` 门禁。R6 还消费 `e100_bootstrap_ci.json` 的结论，但 `provenance` 只有 E109/E125/E126/E127，无法绑定 E100 输入版本。

当前真实 E125 manifest 有 20 个唯一 `(arm,task)`；当前非空 E126 阶段样本长度为 1250；E127 原文件未发现重复键或 NaN；正常与 `python -O` 重跑一致，除 `base_commit` 与约 `1e-14` 的跨环境浮点序列化差异外，当前主数值可复算。因此本项是**已确认的 fail-closed 契约缺陷**，不是“当前所有 E128 数字已污染”的结论。

建议用 schema + 期望笛卡尔积校验所有输入身份；所有派生字段从一个权威原始值重算并逐项联立；绑定完整 arm 配置和输入 hash；检查必需/可选阶段及非空样本数；E127 在建字典前拒绝重复键，并对每个消费数值使用 `math.isfinite(x) and x > 0`。E100 若影响推荐，必须与其他输入一样加载、重算并写入 provenance。
