# Two-Level Indexer：Prefill / Decode 最终实验流程建议

日期：2026-10-08  
状态：实验设计建议；尚未执行本文实验，也未在本轮核查或修改项目代码。  
依据：已核对的代表性论文原文与官方实现。文中的配置、阈值和执行顺序是针对本项目的建议，不是论文已有结果或领域统一标准。

## 1. 最终建议

**保留“先在 decode 筛选策略”的顺序，但不要提前限定论文为 decode-only，也不要让 decode 的单一冠军垄断后续实验。**

推荐执行链：

1. 固定基线、数据划分和阶段开关，先验证实现语义。
2. 在 decode 上低成本筛选，保留精度—速度 Pareto 前沿中的 2～3 个候选。
3. 给 prefill 一次小规模独立复筛机会，补入可能被 decode 排名淘汰的候选。
4. 对入围策略开展 Baseline、P-only、D-only、P+D 四组对照，先固定策略与预算做归因。
5. 确定两个阶段各自适合的配置后，再测试阶段采用不同配置的 P+D 组合。
6. 分别实测 Indexer、Attention 模块、完整模型 prefill、完整模型 decode，以及整请求耗时。
7. 冻结配置，在独立测试集上确认精度和净加速，依据预先规定的标准确定论文主张。

**需要覆盖两个阶段的实验，不意味着最终必须在两个阶段启用同一套 Indexer。最终选择同时受任务精度、完整模型净加速、适用长度和额外开销约束。**

## 2. 其他论文提供了哪些依据

下表区分“方法支持什么”“实验实际测了什么”。这里的 Indexer 泛指为稀疏 attention 选择候选的机制；并非所有方法都是可训练的 Lightning Indexer。

| 工作与原文位置 | 核实到的实验做法 | 对本流程的影响 |
| --- | --- | --- |
| [DeepSeek-V3.2 / DSA，§2.3][R1]；[官方 DeepGEMM][R2] | 分别评估 prefilling、decoding 推理成本；官方提供两个阶段的 Indexer kernel。 | 双阶段方法应分别报告阶段收益；同一选择语义可以使用不同 kernel。 |
| [LongCat LSA，§4.1.2、§4.3][R3] | E2E 配置在所有长度使用 SI、CLI；HI 两级筛选只在 ≥256K 的 prefill 开启，decode 关闭 HI。 | 必须测两级筛选的收益交叉点；不能将整体 LSA 的 decode 加速归因于 HI。 |
| [FASA，§1、§5.3、附录 B.3][R4] | 方法针对 decode；质量覆盖长上下文、语言建模、长推理，并分析输出长度变化。 | Decode-only 是合理定位，但短输出任务不足以证明长生成稳定；需要记录输出长度。 |
| [Quest，§4.2.3、§4.3.2][R5] | 长文本材料先用 full attention；问题／指令逐 token 输入。所谓 E2E 性能测完整模型单步 decode，并排除采样。 | 复现时核对输入切分；不能把论文的 decode E2E 数字解释为整请求加速。 |
| [Kascade，§3.4、§4.1–4.3][R6] | 两阶段均稀疏，但选择粒度不同；明确标出部分对照方法为 decode-only；效率核心是 attention microbenchmark。 | 保留 prefill 独立复筛；图表注明阶段覆盖，区分 attention 与模型 E2E。 |
| [MInference 1.0，§4][R7] | 主实验在 prefill 稀疏、decode 保持 dense，另测与 decode KV 压缩组合。 | P-only 同样是成立的研究定位；组合效果需要额外验证。 |
| [HISA，§4.1、§5、§7][R8] | 粗筛后用原 DSA 打分细筛；固定最终 token 预算，并区分短前缀退化行为和 kernel／E2E 边界。 | 分别控制粗筛候选数和最终预算；补充全扫描细筛对照，检验层级筛选的真实增益。 |
| [MISA，§5 设置、§5.3、§7][R9] | 明确两阶段使用路由；性能主要测 Indexer kernel，局限部分明确未测完整模型 E2E。 | “双阶段启用”和“双阶段模型 E2E 已证明”是不同证据；我们的实验应补齐后者。 |

因此，应修正“近期论文都是双阶段测过，所以必须双阶段上”的理解：**代表工作存在 P-only、D-only、P+D，以及按阶段／长度开关模块的不同做法。我们应学习它们的评测边界，而不是只模仿最后的加速比。**

## 3. 先固定项目问题与对照口径

### 3.1 本轮要回答的四个问题

- Two-level 相对单级／全扫描筛选，能否减少索引代价并保持任务质量？
- 这种收益分别出现在 prefill、decode 的哪些长度和 batch 范围？
- 两阶段组合后，质量损失是否仍可接受，整请求是否更快？
- 子空间、near/far 划分、粗筛、细筛各自贡献了什么？

沿用此前约定的算法顺序：**先子空间，再分 near/far，两端分别 L1 粗筛＋L2 细筛，最后完成预算合并与稀疏 attention。**这是设计基准，不代表本轮已确认代码实现一致。

前 4 层 full attention 可作为沿用配置，但必须写入配置文件，并在本轮开始时核对。Near-only、跳过 far、不同层预算等作为后续独立消融，不要在首轮四组归因中一起改变。

### 3.2 必须固定与记录的条件

| 类别 | 必须记录的内容 |
| --- | --- |
| 模型 | Checkpoint/revision、模型结构、tokenizer、chat template、RoPE 设置、权重及 KV 精度 |
| 方法 | 子空间选择与维度、near/far 定义、L1/L2 组合、粗筛预算、最终预算、sink/window、启用层 |
| 阶段 | Prefill/Decode 开关、chunk 大小、首 token 边界、fallback 条件、query/头共享方式 |
| 实现 | 仓库 commit、kernel 后端、实际命中路径、CUDA Graph／编译模式 |
| 环境 | GPU 型号与数量、软件版本、batch／并发、TP/PP、KV 分片、offload、MTP 是否启用 |
| 任务 | 数据版本、样本 ID、输入长度、生成参数、输出上限、seed、计分脚本版本 |

对普通 dense 模型，四组中的基线使用同一 checkpoint 的 full attention。若研究对象是原生 DSA 模型，则主基线应是同一 checkpoint 的原生 DSA；不能将“强行切为 dense”或另一个 dense checkpoint 当成完全等价的基线。本文下文以普通 dense 模型为例，原生稀疏模型按这一规则替换基线。

### 3.3 数据划分与调参边界

- **校准集**：确定子空间、静态统计或聚类初始化等，按方法需要使用。
- **开发集**：筛选 method、预算、阶段配置和长度阈值。
- **测试集**：配置冻结后确认结果，不用测试分数反复挑冠军。

小样本初筛使用固定样本清单，覆盖不同任务和长度，不能每个方法抽不同题。校准数据不得含测试答案；若索引需要读取当前请求的 prompt，这是在线计算，其成本要计入请求。

## 4. 阶段 A：正确性与阶段开关验证

先过这些检查再跑大规模精度，避免选出“绕过了稀疏路径”的假冠军。

### 4.1 四种模式必须真实独立

| 模式 | Prompt 的 attention | 后续生成步骤的 attention | 提醒 |
| --- | --- | --- | --- |
| Baseline | Full | Full | 基线输出与耗时 |
| P-only | Two-level | Full | Decode 仍消费稀疏 prefill 产生的 KV |
| D-only | Full | Two-level | Prefill 为 decode 建索引的成本仍属于请求 |
| P+D | Two-level | Two-level | 使用本模式自己产生并持续更新的状态 |

**不能让 P-only 或 P+D 直接复用 Baseline 保存的整套 KV 来做最终精度评测。**那会掩盖 sparse prefill 对隐藏状态和后续层 KV 的影响。固定 dense Q/K/V 回放可用于局部诊断，但不等于真实生成实验。

常见生成接口中，第一个输出 token 来自最后一次 prefill 前向的 logits；明确记录这一边界。若为了复现 Quest 将问题也逐 token 输入，需要给所有对照应用相同切分，并单独标记为“论文复现协议”，不要与标准整段 prompt prefill 混表。

### 4.2 优先排查与本方法直接相关的错误

- 同一选中集合下，优化 kernel 的输出应与稀疏参考实现一致；数值容差按 dtype 预先设置。
- 预算覆盖全部有效历史 token 时，应退化到对应 full-attention 参考结果。
- Prefill 的可见性按每个 query 位置限定，不能只在最终 attention 才加 causal mask：子空间在线统计、cluster／block summary、L1/L2 打分也可能泄露未来信息。
- 当前未完成 block、chunk 边界、packed sequence 边界、padding 和位置偏移必须处理正确。
- Near/far 合并去重；sink/window 与动态候选的重叠只计一次。候选不足或重复后是否补齐，需要有确定规则。
- 检查短序列、非整 block、跨 chunk、增量更新、batch 内不同长度和全部落入 near 的情形。
- 若 prefill 采用 query-tile 共享索引，要写明共享粒度及因果处理；这是可能影响精度的算法选择，不能仅视作无损 kernel 优化。

产出：一份通过／失败记录，以及各模式实际稀疏层数、query 数、fallback 比例与有效预算日志。这里的日志用于验证执行路径，正式计时关闭重型 profiler。

## 5. 阶段 B：Decode 初筛＋Prefill 复筛

### 5.1 Decode 初筛：保留前沿，不急于唯一冠军

在当前项目实际支持的 method 组合中选择候选，不凭本文新增或虚构组合名称。聚类原语如影响构建与更新成本，应作为显式配置记录。

先在一个代表模型、短／中／长三个长度档和固定开发集上运行 D-only。长度可从 8K、32K、128K 起步，但必须服从模型有效上下文与显存限制。

每个策略先使用相同最终 attention 预算，粗筛候选预算记录实际值；再为入围者做少量预算扫描。逐步记录：

1. 最终任务分数及分任务损失。
2. 长生成任务上的正确率、输出长度、截断率。
3. Indexer 总耗时、attention 模块耗时、完整模型 TPOT。
4. 构建／更新成本和额外显存。

保留 2～3 个具有代表性的 Pareto 候选，例如质量较高者、均衡者和更快者。若差异落在噪声范围内，先视为并列；在重复测量后仍并列，可以优先选择实现更简单、开销更稳定的方案。

### 5.2 Prefill 复筛：给不同执行特性一次机会

对 decode 入围者做小规模 P-only 精度和完整 prefill 性能测试。再从剩余正确候选中，补测少量具有低构建代价、较好批量复用或不同选择粒度的方案。

这一轮只用于避免 decode 筛选偏差，不要求重新穷举所有组合。不能因为某方案在 decode 慢，就直接断言它在 prefill 无效。

分别得到候选集合 C_D 和 C_P，合并后建议控制在 3～4 个以内进入归因实验。候选都明显不达标时，回到算法或实现诊断，而不是人为选一个“冠军”。

### 5.3 共同采用的两个比较视角

- **等最终预算**：比较选择质量及选择器开销；同时报告粗筛预算、block 取整和实际加载量。
- **等质量目标**：在开发集预设质量阈值，比较每种方法达到阈值时的最快配置，冻结后在测试集确认。

同 token 数不等于同字节流量，也不等于相同时间；固定预算与相对预算分别标注。最终论文至少给出质量—延迟曲线，而非仅有一个最有利的点。

## 6. 阶段 C：四组归因，然后才做阶段调优

### 6.1 先做同配置的四组对照

对同一候选保持子空间、层掩码和预算规则一致，仅改变 P/D 开关。分配预算需要依赖历史长度时，保持同一个函数形式。

| 对照 | 主要回答的问题 |
| --- | --- |
| Baseline → D-only | 固定 dense prefill 后，稀疏 decode 对生成有什么影响？ |
| Baseline → P-only | 稀疏 prefill 改变上下文表示后，完整 decode 能保留多少质量？ |
| Baseline → P+D | 实际双阶段使用的联合质量损失是多少？ |
| P-only、D-only → P+D | 两阶段组合是否出现额外退化？ |

对“越高越好”的同一任务分数，定义：

\[
\Delta_P=A_0-A_P,\quad \Delta_D=A_0-A_D,\quad \Delta_{PD}=A_0-A_{PD}.
\]

可辅助报告：

\[
I=\Delta_{PD}-\Delta_P-\Delta_D.
\]

I>0 表示在这个分数尺度上联合损失超过两项损失之和。**它是固定实验配置下的描述性交互量，不是一般误差传播定律或机制证明。**分别给出配对置信区间，不用不同任务的原始分数直接相加。

### 6.2 再做阶段采用不同配置的组合

若两阶段最适策略或预算不同，再测试以下小范围组合：

- Prefill 最优配置＋decode 最优配置。
- 共享 method，但使用不同的粗筛／最终预算。
- 短上下文回退原路径，超过实测交叉点后启用 two-level。

此时需要再次完整测试 P+D 精度；两个单阶段候选各自合格，并不能保证组合合格。若索引表示不同，阶段切换时的转换、重建、额外驻留显存均需计入。

长度阈值只在开发阶段选定，并按目标硬件、batch 和并行方式记录；不能照搬 LongCat 的 256K，也不能看测试集答案后动态选择。

## 7. 阶段 D：精度评测与判定标准

### 7.1 至少覆盖两类主任务和一类诊断

| 类别 | 建议选择 | 必须观察 |
| --- | --- | --- |
| 长输入、短／中输出 | 固定版本的 LongBench；需要更长长度时加受控检索／多跳任务 | QA、摘要、代码等分项质量；不同长度是否突然退化 |
| 短／中输入、长输出 | 适配模型能力的 MATH500 或 AIME 类长推理任务 | 最终答案分数、生成长度、截断率、重复／提前终止 |
| 受控诊断 | 多位置、多目标检索；PG19 等语言建模评测可选 | 长度与目标位置敏感性；teacher-forcing 下的预测变化 |

这些是建议的任务类别，不要求每轮把所有 benchmark 跑一遍。开发阶段使用固定子集；最后对入围配置执行预先确定的正式评测范围。若只验证一个模型，论文应相应限定泛化主张；若主张通用，至少补一个不同架构或模型家族。

PPL 评测明确采用全序列、chunked 还是逐 token 前向，以及评测位置；全序列 PPL 不能自动证明 autoregressive decode 路径已启用。

### 7.2 什么叫“精度损失可接受”

在正式测试前，为每个主任务确定容忍度 epsilon_j，不从结果倒推。百分制准确率使用“百分点”表述，其他指标保留原量纲。若需要一个开发阶段的临时筛选值，可暂用主指标绝对下降 1 个百分点；这只是可调整的筛选建议，不应当成所有任务的最终标准。

对测试样本进行配对比较，建议按题目／文档重采样计算质量损失的 95% 置信区间。对多次随机生成，题目内的多次输出相关，不当作完全独立题目扩大样本量。

只有当损失置信区间上界不超过预设容忍度，才有充分依据声称在该范围内保持质量。区间过宽时结论为证据不足；“差异不显著”不等于“等效”。关键任务的明显退化不能被平均分掩盖。

### 7.3 Token overlap、attention mass 的定位

Recall/IoU、累计 attention mass、attention 输出误差及 logits/KL 变化，只用于解释失效和缩小调试范围，不能替代任务分数。

可增加三层诊断：

1. 固定 dense 回放轨迹，判断粗筛漏掉什么、细筛能否恢复。
2. 模式自身的 teacher-forcing 轨迹，观察状态变化。
3. 真实自由生成，确认最终任务影响。

用完整 attention 分数选 Top-k 的参考，可用于诊断预算及选择误差，但它不是任务质量的严格上界；完整 attention 也不是所有离散任务分数的数学上界。

## 8. 阶段 E：性能计量，明确每个加速比的分母

### 8.1 四个层级分别测量

| 层级 | 计时范围 | 合适的参照 |
| --- | --- | --- |
| Indexer 热路径 | 在线投影／打分、粗筛、候选整理、细筛、Top-k、去重和必要更新 | 同语义全扫描／单级 selector；原生 DSA 场景用 DSA indexer |
| Attention 模块 | 以输入 Q/K/V 到 attention 输出为界，包含选择器、必要数据准备和 sparse attention | 相同输入边界的优化 full attention，或明确的原生稀疏基线 |
| 完整模型阶段 | 全部层、FFN、必要 LM head 等；分别测完整 prefill 和完整 decode 步骤 | 同模型、同精度、同运行设置的基线 |
| 整请求 | Prompt 处理、阶段转换、生成至结束或固定长度，包含在线建索引 | 相同请求与计时边界的基线 |

离线共享校准开销单列；**每请求构建／聚类不能伪装为离线成本**。若为了 D-only 在 prefill 建索引，必须计入 D-only 的 prefill／整请求耗时；若延迟到首个 decode 构建，则计入该处。

分别定义：

\[
S_{idx}=T_{idx,ref}/T_{idx,ours},\quad
S_P=T_{P,ref}/T_{P,ours},\quad
S_D=TPOT_{ref}/TPOT_{ours},\quad
S_{req}=T_{req,ref}/T_{req,ours}.
\]

各比值必须在相同 workload 上计算。Full attention 没有独立 selector 时，S_idx 不存在对应分母，标为 N/A；不能把 full attention 时间除以 Indexer 时间当作 Indexer 加速比。

### 8.2 正确定义 prefill、TTFT、decode 和整请求

- **完整 prefill 耗时**：直接测整个 prompt 的模型处理，chunked prefill 累加所有 chunk 和相关准备，不能只测最后一个 chunk。
- **模型内 TTFT**：如包含采样、初始化或其他工作，写明范围。它与服务端 TTFT 不是同一个指标。
- **服务端 TTFT**：只有实测服务请求时才使用该名称，明确排队、tokenization、网络是否包含。
- **TPOT**：给出生成 token 数与计时边界；标准首 token 已计入 TTFT 时，可用 (请求生成耗时−TTFT)/(输出 token 数−1)，输出数必须大于 1。
- **整请求耗时**：直接实测，不把独立最优的 S_P 与 S_D 拼接为一个不存在的配置。

只有做机制解释时，才用近似式：

\[
T_{request}\approx T_{setup}+T_{prefill}+\sum_{t=1}^{N_{out}-1}T_{decode,t}+T_{other}.
\]

所有项互不重复计费；setup 若已在阶段计时中则不再单加。Decode 延迟会随 KV 增长，长生成不能仅用初始位置的单步 TPOT 代表全程。

### 8.3 固定工作量与自然生成分开报告

**固定工作量测速**：固定输入／输出长度、batch 和上下文档位，隔离实现速度。若强制生成固定长度或使用 token 回放，需要标明这是性能协议，不拿该输出评估任务质量。

**自然生成任务**：保留正常 EOS 和任务生成协议，同时报告质量、真实输出长度、截断率和总耗时。质量测试不为对齐速度而强制输出相同长度。

二者都需要：固定工作量防止“少生成导致假加速”，自然生成反映真实任务成本。[FASA][R4] 和 [Kascade][R6] 的输出长度分析说明，这个因素会改变最终收益，不能忽略。

### 8.4 长度、batch 与开销交叉点

先覆盖一个短档、两个主工作区间、一个能力上限附近档位。若模型仅可靠支持 128K，不把更长长度的结果混作有效模型精度；更长的合成 kernel 测试单独标明。

Decode 至少测试 batch=1 和一个符合实际负载的更大 batch；prefill 至少测试完整 prefill 与实际使用的 chunked prefill。不要因某配置 OOM 而悄悄降低它的 batch 后继续计算同表加速比。

记录 actual_sparse_query_fraction、有效候选数、fallback 率和额外峰值显存。若大部分 query 实际回退 dense，“精度不掉”并不能充分验证稀疏方案。

### 8.5 排除性能噪声的最低要求

- 在可控空闲 GPU 上比较，记录其他负载、频率／功耗状态和内存占用。
- 预热到编译、缓存和延迟趋于稳定；JIT／冷启动时间另报。
- 建议从 5 个独立重复轮次开始，每轮交错或随机安排基线与候选；kernel 内循环另计。
- GPU kernel 用适当同步的设备计时，模型／请求用同步后的 wall-clock；多 stream 工作必须全部覆盖。
- 报告中位数、离散程度和轮次层面的加速比区间。小于波动范围的差异判为未决，针对该点重测。
- 不用 profiler 内的结果作为最终延迟；不只选择最快一次。不能把强相关的同轮重复当作大量独立证据。

并行跑任务可用于加速精度评测；做延迟基准时避免同卡任务互相干扰。

## 9. 阶段 F：对照方法与必要消融

### 9.1 对照分三组，避免混淆目标

| 对照组 | 建议内容 | 回答的问题 |
| --- | --- | --- |
| 同模型的基线 | 优化 full attention；原生稀疏模型使用原生路径 | 最终用户获得多少收益？ |
| 阶段匹配的外部方法 | D-only 可选 Quest/FASA；P-only 可选 MInference；P+D 可选 Kascade，取决于模型和实现兼容性 | 同类部署目标下是否有竞争力？ |
| 同 selector 的机制对照 | 全扫描细筛、仅粗筛／block 选择、完整 two-level；适用时再对照 HISA 类层级方法 | 收益究竟来自层级设计还是其他改动？ |

不是要求把每种方法都移植到每个模型。先选择结构适配且可可靠复现的强对照，无法兼容的论文用于相关工作分析。不能把 DSA 的 learned indexer 原样当作无 indexer 的 GQA 模型上的免费基线。

主表采用统一任务协议；按论文原协议复现的数据单列。方法未支持某个阶段时标明 N/A，不自行扩展后仍沿用原论文名字。保留其公开质量敏感设置，另外给出受控消融，不将被削弱的基线作为主结论。

### 9.2 本项目优先做的消融

1. **全扫描细筛 vs. L1＋L2**：最终预算、子空间和细筛公式相同，衡量层级搜索节约与粗筛损失。
2. **粗筛候选预算扫描**：找出质量恢复与性能收益的平衡点。
3. **子空间选择／维度**：其余规则固定，解释子空间的作用与开销。
4. **统一区域 vs. near/far 分区**：总预算一致，检验分区的独立价值。
5. **P-only／D-only／P+D**：阶段覆盖与交互，属于主实验而非可省略的附录细节。
6. **层选择或跳过 far**：仅在实际实现且主张该能力时追加，不与主流程一次性混改。

关闭 L1 时，允许候选退化为全部历史并使用同一 L2；关闭 L2 的预算处理应明确。如果两级共享不同打分公式，不将这一对照称为完全等语义。

## 10. 执行顺序、产物与停止条件

| 顺序 | 工作 | 产物／通过条件 |
| --- | --- | --- |
| 0 | 冻结实验范围、数据划分、质量标准与阶段边界 | 实验配置与样本清单；四种模式定义明确 |
| 1 | 正确性和路径验证 | 稀疏参考一致、因果与更新正确、实际启用日志可查 |
| 2 | D-only 开发集初筛 | 2～3 个有证据支持的 Pareto 候选 |
| 3 | 小规模 P-only 复筛 | 补入 prefill 有潜力候选；候选总量受控 |
| 4 | 同配置四组归因 | 每个候选的四组质量和阶段延迟 |
| 5 | 有限阶段调优与交叉点测试 | 冻结最终配置；必要时包含阶段不同配置方案 |
| 6 | 独立测试集确认及完整性能测量 | 质量区间、S_idx/S_P/S_D/S_req、显存与长度分布 |
| 7 | 针对主张的消融与论文组织 | 贡献证据链完整，负结果与适用边界保留 |

优先在能容纳的代表模型上完成单 GPU 或最小必要并行配置。是否增加多卡实验取决于论文是否主张分布式收益，或模型／上下文本身是否需要；多卡不能代替单方法的效果归因。

独立 two-level 库加一个实际运行的模型适配器即可测模型 E2E，不以修改 SGLang 为前提。若主张生产服务吞吐，则另需真实服务适配与负载实验。SGLang 代码改动遵循既有约束，由用户另行触发。

若质量不达标，先定位粗筛漏选、预算、子空间或状态更新；若 Indexer 更快而模型不快，先分析时间占比和额外准备开销。已经足够证明或否定一个候选时停止无关扩测，不为凑“冠军”继续挑有利样本。

## 11. 最终结果表与论文定位

### 11.1 建议保留的三张主表

**质量表**：模型、任务、长度、method、P/D 开关、预算、基线分数、方法分数、损失及区间、输出长度、截断率。

**性能表**：模型、长度、batch、chunk、method、P/D 开关、构建时间、Indexer 时间、attention 时间、prefill 时间、TPOT、固定长度整请求时间、自然生成整请求时间、峰值显存和加速比分母。

**归因表**：同一候选的 Baseline/P-only/D-only/P+D 四组，以及必要的 I 描述量。阶段分别调优后的组合另列，避免与固定配置归因混在一起。

在原始记录中让 quality_run_id 和 perf_run_id 共享同一 method_config_hash、模型版本和阶段策略。不同测试 workload 可以不同，但算法配置差异必须显示出来；不能拼接来自不同预算的“最佳精度”和“最佳速度”。

### 11.2 论文定位的预设规则

| 测试结果 | 建议主张 | 必须保留的边界 |
| --- | --- | --- |
| P、D 都有可靠净收益，P+D 质量达标 | 双阶段高效 Indexer／稀疏 attention | 分别给 S_P、S_D 与整请求收益 |
| 只有 D 稳定获益 | Decode 为核心 | 报告 prefill 结果与开销／质量原因 |
| 只有 P 稳定获益 | Prefill 为核心 | 报告 decode 不划算的长度与 batch 范围 |
| 两阶段需不同预算／策略 | 按阶段配置的统一框架 | 规则在开发集固定，报告组合精度和切换成本 |
| 只在长上下文获益 | 有长度阈值的方法 | 短上下文回退及阈值附近测量 |
| 只有 Indexer 快，模型收益不足 | Indexer 算子／选择器优化 | 不宣称模型或整请求 E2E 加速 |
| 精度区间太宽或质量下降超过阈值 | 暂无充分保精度证据 | 扩充针对性验证或调整方法，不能称无损 |

论文故事应由这些预设判据约束。即便最后选择 D-only，也保留 P-only 和 P+D 的有界验证结果；它们解释方法的适用范围，并证明我们没有未经测试就排除另一阶段。

## 12. 最终验收清单

- [ ] 四种阶段模式真实可用，首 token 与 chunk 边界有定义。
- [ ] Prefill 的选择过程和统计没有未来 token 泄漏。
- [ ] Decode 初筛没有永久排除 prefill 潜力候选。
- [ ] 配置先在开发集选择，再在独立测试集确认。
- [ ] 精度包含长输入与长生成，并报告分项和输出长度。
- [ ] P-only／P+D 使用自身轨迹的状态，未偷用 dense KV。
- [ ] Indexer、attention、模型阶段、整请求加速比各有正确分母。
- [ ] 在线构建、聚类、更新、阶段转换与真实 fallback 已计入。
- [ ] 固定输出长度测速与自然生成成本分别报告。
- [ ] 有重复测量和噪声判断，不能靠单次峰值宣布领先。
- [ ] 质量与性能使用一致算法配置；所有局限与负结果保留。
- [ ] 最终定位由质量和净收益共同决定，不预设 decode-only 或双阶段必胜。
