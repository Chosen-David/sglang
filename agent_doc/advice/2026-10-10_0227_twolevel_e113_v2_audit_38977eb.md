## 复现证据

### 1. 失败重跑保留旧成功产物（054）

使用原文件直接导入并调用生产 `main()`；只把 GPU/张量/实现加载替换为最小 CPU
桩，使执行确定进入原始 `errs` 分支。输入路径先放入旧成功 JSON（内容
SHA256 `a277464e19754400d9371b464e212c05219e64cc161628b896836644f9490d2b`）及旧
sidecar，再注入 `forced mismatch`。实际输出：

```text
[GATE-FAIL] ["forced mismatch"]
correctness 门失败 → 不发布性能 JSON；失败日志 -> <tmp>/result.json.failure.json
{"exit_code":1,"failure_exists":true,"old_sidecar_still_exists":true,"old_success_content":"{\"status\":\"old-success\"}","old_success_still_exists":true}
```

末行 SHA256：
`06f09e95a3e2bf09d81bcab3aa39a76f251c5af29a75a4e8bec0f54fe3ba6781`。

实际行为是：退出码为 1、failure 落盘，但旧成功 JSON 与旧 sidecar 同时继续存在。
若消费者只按 `result.json`/sidecar 存在和哈希闭合读取，就会把失败重跑之前的结果
继续当成本次成功。生产失败分支没有 run/attempt ID，可见文件也无法区分代际。

反向状态转换同样复现：先放旧 failure（内容 SHA256
`38521bb0c7edbd957bce6bbfd0d53ea80d25a555e8b09e1d4e46bb64fa028925`），再让原始
`main()` 走完整成功发布循环，结果为：

```text
{"sidecar_exists":true,"stale_failure_content":"{\"status\":\"old-failure\"}","stale_failure_still_exists":true,"success_exists":true}
```

末行 SHA256：
`3968b036c609246d38ef3d86958eab4e6b155cbe4cf8505e7a1990a40d48fca6`。

`e113_failclosed_inject.py:30-33` 在调用生产入口前删除 `OUT`、failure 和 sidecar，
所以它只证明“全新空路径上的首次失败不新建成功文件”，没有覆盖同路径重跑。

### 2. “原始延迟”已经舍入（055）

生产代码先对计时列表执行 `ts.sort()`，再在写 JSON 前执行：

```python
"wall_s_python_samples": [round(s, 4) for s in ref_samples],
"wall_s_triton_samples": [round(s, 5) for s in tri_samples],
"speedup": round(t_ref / t_tri, 1)
```

对归档的 10 个 case 以 `median(persisted_python_samples) /
median(persisted_triton_samples)` 复算，示例：

```text
T=1024  structured_c8  stored=211.2  recomputed=210.8962
T=16384 structured_c8  stored=32.0   recomputed=31.9655
T=32768 singleton      stored=3.7    recomputed=3.6567
```

当前 `e113_microbench_v2.json` 文件 SHA256 与 sidecar 均为
`2cbbc9e6f55cc75eca2783a775345313e1d05c8a78ab578c0c4281e99a47f27b`，内嵌
content SHA 也按脚本口径自洽；问题不是文件被篡改，而是发布前已经丢失原始计时精度。
排序还丢失了采样发生顺序，且 Python `rep=1`、Triton `rep=3` 不是 paired samples。因此归档
本身不能支撑把某个离群值对应到“首轮升频”或复查随时间变化的漂移；若该判断来自独立遥测，
应把带时间戳/clock/temperature 的同次采样一并绑定。

## 修复与最小重测建议

1. 把一次尝试作为不可变 generation：先在唯一 run/attempt 目录写齐 success 或 failure
   receipt，再原子更新唯一指针；消费者必须核对指针、attempt ID、状态与内容 SHA。这样无需
   删除历史，也不会让旧成功与新失败共享同一身份。
2. 若暂不引入 generation，至少在开始新 attempt 时隔离旧 `out`/sidecar，并在失败 receipt
   中记录 attempt ID；成功发布时原子撤销同 attempt 的 failure。不要用“测试预先清场”代替
   生产状态机。
3. 为 054 增加两个 CPU 状态转换负例：`旧成功 → 新失败`、`旧失败 → 新成功`；断言消费者
   永远只能解析出一个与本 attempt 匹配的终态。测试须调用生产入口/发布 helper，不能在测试
   自己先删目标来制造空目录。
4. 计时样本按执行顺序保存整数纳秒（优先 `perf_counter_ns` 或 CUDA event 原始 tick），所有 median、
   `us_per_token`、speedup 从**已持久化原始值**统一派生；增加“读回 JSON 复算逐位一致”测试。
   若继续称 paired，双方须同次数、交错或随机化顺序并记录 pair；否则改称独立重复样本。
5. GPU 重测只需受影响的最小矩阵：至少一个结构簇和一个 singleton case，固定同一实现、输入
   hash、GPU 空闲口径；054/055 的 CPU 红绿先过，再决定是否重发完整 v3 性能 JSON。
