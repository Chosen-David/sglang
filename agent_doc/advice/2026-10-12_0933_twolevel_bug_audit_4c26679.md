## 3. 复现证据与违反契约

### 3.1 `111`：评分字节与验证字节不是同一快照

`eval.py:261-272` 已把 JSONL A 解析到内存后，`validate_runcap_sidecar()` 才在
`:325-326` 重开 sidecar 和 JSONL 计算 SHA/行数。producer 锁只约束 producer，
consumer 从不获取；JSONL 又由 `pred.py:759` 直接 `open(..., "w")` 覆盖。

受控交错为：eval 读 A → 同 identity/cap producer 完成 B+sidecar B → validator
验证 B → scorer 继续使用 A。实际输出：`scored_predictions=["GEN_A"]`，当前验证
文件为 `GEN_B`，validator 返回 B SHA，`mismatch_accepted=true`。

- 复现脚本 SHA256：`53a5dbbeb141a46fdc131232fb19fd6f95aeba85a23364a672b6440bbbbb8c4d`
- 原始日志 SHA256：`07293a80cb2af088d62eee5eedff1000b5a7f4616589f4d84e05f0e8c9d1d6ac`

违反契约：评分、SHA、行数和 provenance 必须绑定同一不可变字节快照，而不是同一路径
在不同时刻的不同版本。

### 3.2 `112`：正常同 cap 多任务被误判“混 cap”

`cap_identity_payload()` 明确含 `dataset`、`dataset_fingerprint`、
`run_timestamp`、`max_new_tokens` 等 run 字段；`eval.py:342-349` 却要求所有任务的
这个完整 hash 唯一。实际调用 evaluator，两个 `effective_cap=protocol_cap=16384` 的
任务得到 hash `2f118d15c2` 与 `da635d8118`，随后以“混挂 2 个不同 cap identity”退出，
未写 `result.json`。

- 复现脚本 SHA256：`b6c8ebd578ac55b540ac1e9f50f5d2baaad0a3f90213d61c312abd9492c93f06`
- 原始日志 SHA256：`edbc2afd3f7bc3c4315f9363178ed7223f5d72d14bd22bb35e841343f0cd8f63`

违反契约：跨任务只应比较 cap 语义，不应要求不同数据集/时间戳拥有同一 run identity。

### 3.3 `113`：strict 与 cap-unknown legacy 被发布到同一表

实际 evaluator 反例由一个合法 strict JSONL 与一个显式允许的 legacy JSONL 组成。
结果仍写出，包含两个任务分数；`_meta.runcap` 同时为
`strict_validated=1, legacy_no_sidecar=1`，却带非空 `cap_effective=16384` 和 strict
identity，`mixed_table_published=true`。

- 复现脚本 SHA256：`cea7a783435ac9a3169f610802767aec3e460fae80254e73c8f3aae0cad920f5`
- 最终 SHA 重跑日志 SHA256：`24fae80a4b70c16fd40f778bbf4d14d22234ce4c18a782e07984d80019f2f5dc`

违反契约：代码警告 legacy “cap 身份未知，不入 cap 敏感聚合”，但实现仍把它并入
带 cap 标签的同一结果表。

### 3.4 `114`：提交前已并发修复并复查通过

在本轮最初审查的 `85eba1f`，锁路径固定为输出目录的 `.runcap_gate.lock`；两个不同
输出文件的 CPU 反例中，持锁 1.2 s 时第二进程等待 `1.200197 s`。提交前 refetch
发现 `7367367` 已把锁改为 `out_path + ".runcap_gate.lock"`。在最终审查 SHA
`4c26679` 重跑同一反例，第二任务仅等待 `0.000502 s`，`serialized=false`。

- 复现脚本 SHA256：`d858849bb0ac8bcedff46aa2aaa2e3aa5b76d1090ea6927ff4dd03815fd6a3ab`
- 最终复查日志 SHA256：`f9513c5f3685f9940ed2def275a8f8ad75c0f465ea2d712fb01bef121c53156d`

因此该项不再作为当前未决缺陷；未在真实 8 卡环境测吞吐，但锁粒度的 CPU 并发契约已
恢复。保留记录用于避免把同轮已修复问题重复交付。

### 3.5 `115`：identity/schema 未做密码学与字段闭包校验

基于项目真实 `build_run_cap_core()` 与 `finalize_run_cap_manifest()` 生成合法 manifest，
随后仅把外层 `effective_cap: 16384 → 31500`、`result_file → other.jsonl`，保留原
payload/hash。`validate_run_cap_manifest()` 仍返回成功：

```text
outer_effective_cap=31500, payload_effective_cap=16384,
stored_identity_hash=recomputed_identity_hash=4efdab702f,
result_file=other.jsonl, validator_accepted=true
```

- 复现脚本 SHA256：`aeac694a5b69090773273e92bdea5723047914bae1e7562ca0149ae39fa5d27d`
- 原始日志 SHA256：`139356a2589701b7f27b31545101e7aab84ba0edfd4d37bb29de11aab6872638`

`eval.py:104-110` 又直接信任外层 cap 且不检查 sidecar 的 `result_file` 是否等于当前
JSONL basename。误拷、手改或错误 backfill 后可把有效结果静默标成另一 cap/文件。

### 3.6 `116`：kernel host 门接受危险 K/V 形状

抽取并执行真实 `_validate_gqa_shape()`，输入
`q=[1,1,32,128]`、`k=[1,16384,8,128]`、`v=[1,1,8,128]`、
`mask=[1,8,16384]`，门返回 `true`。`_eager_attn_kernel` 在
`:220-223` 以 token `tok` 访问 K/V，而 wrapper 在 `:327-330` 同时给二者传入
`k.stride(0), k.stride(1)`；V 的实际 token 长度/stride 并未传入或核对。

- 复现脚本 SHA256：`cdb109e11b875097377a8fa285e31c5aa0de0770aa16473f74a1edbc3876b893`
- 原始日志 SHA256：`c484ee3db764752d2d19b313fe6f8de749f9a1fde74d43d4a7916b4fe7ba0b45`

CPU 反例确认入口漏拒；因本机无 Triton/GPU，未执行实际越界读。基于寻址式，任何
`tok>=1` 对上述 V 都超出其 token 范围；即使 token 长度一致，只要 V stride 与 K
不同也会错址。正常 Qwen 连续同形 K/V 不触发，历史 E127 数值不能据此判为污染。

## 4. 对已跑数据/实验的影响

1. `111` 仅影响 evaluator 与同路径、同 cap 重跑并发重叠的窗口。当前没有证据证明
   已发布分数命中；应按日志、进程时段、JSONL/sidecar mtime 核查，命中者需从冻结
   JSONL 重新聚合。
2. `112` 使新 strict sidecar 口径下的正常多任务 `result.json` 无法生成，是可用性
   阻断；已有 strict JSONL/sidecar 本身无需 GPU 重跑，修复 evaluator 后重新聚合即可。
3. `113` 只影响显式启用 `--legacy-no-runcap` 且目录同时含 strict/legacy 的表。仓库内
   未找到证明现有正式表命中的证据；需查当前历史结果的 sidecar 覆盖率。
4. `114` 在最终 SHA 已 fixed/rechecked；旧 `85eba1f` 窗口只影响吞吐/墙钟，不改变
   数值。未取得远端部署 SHA/日志，不能断言曾运行的批次命中过旧目录锁。
5. `115` 影响误拷/手改/backfill 错配的 sidecar。尚无证据表明已有正式表被错误 cap
   标记；应重算每份 payload hash并核对 payload↔外层字段、sidecar↔result basename。
6. `116` 影响未来或异常调用的不同形 K/V、非同 stride/device/dtype 输入。当前生产
   Qwen 配置通常传同形连续 K/V，未证明历史 E127 数据受影响。

## 5. 修复与最小重测建议

- `111`：consumer 使用与 producer 相同的**每输出目标**锁，在一个锁窗口中一次读取
  JSONL bytes 和 sidecar，并从同一 bytes 完成 parse/SHA/行数/评分。更稳妥为不可变
  generation 文件 + 原子指针；仅前后 `stat` 不能排除 ABA。
- `112`：新增独立的 cap-comparability key，只含允许跨任务统一的 cap 语义
  （effective/protocol/treatment，必要时模型/配置）；完整 run identity 继续用于单文件
  防覆盖，不参与多任务 cap 等价判断。
- `113`：同一结果表只要同时出现 strict 与 legacy 就 fail-closed；全 legacy 只能显式
  模式并将 cap 字段全部置 null，或先补齐 sidecar 后再聚合。
- `114`：`7367367` 已完成结果文件级锁，并新增“同目标阻塞、不同目标并行”回归；后续
  只需让 `111` 的 evaluator 复用同一 lock-key 函数。
- `115`：schema 门重算 canonical payload hash；逐字段核对 payload 与外层
  model/dataset/fingerprint/method/timestamp/cap/treatment/max_new_tokens；consumer 核对
  `result_file == basename(jsonl_path)`。对存量 sidecar 批量只读审计后再启用强门。
- `116`：launch 前要求 K/V token 长度、head 数、head_dim、device、dtype 一致，并明确
  支持的 layout；要么强制 contiguous，要么向 kernel 分别传 K/V 的 token/head/d stride。
  添加小/空/非整块、不同 stride、K/V 短长不一、head_dim 不同的拒绝与 GPU sanitizer
  测试；合法连续输入与 dense reference 做 fp32/bf16 差分。
