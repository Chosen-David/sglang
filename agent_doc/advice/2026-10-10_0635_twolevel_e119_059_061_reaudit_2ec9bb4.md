## 1. `TL-E119-YARN-SNAPSHOT-RACE-062`

### 违反的契约与位置

`two-level-attention/benchmark/RULER/score_ruler_formal.py` 在本次实现提交：

- `:405-412` 先从可变源路径读行并把 native 预测复制到 staging；
- `:607-610` best-file 仲裁和后续评分均使用 staging 副本；
- `:649-654` 之后才调用 `_load_producer_yarn_receipt`，该函数在 `:467-499` 重新打开**源路径**，验证源当前 SHA/行数与当前回执；
- `:670-672` 又分别现算源 SHA 与 staging SHA，但没有断言两者相等，也没有断言 staging SHA 等于回执 `prediction_sha256`。

生产者在 `yarn_receipt.py:277-278` 通过两次 `os.replace` 提交新预测与新回执，并只在生产者之间使用咨询锁；formal 消费者没有获取同一锁。因此以下正常时序可达：

1. formal 打开 A 并复制 A 到 staging；
2. 生产者完成 B，原子替换源预测和回执；
3. formal 验证当前源 B 与当前回执 B，一致；
4. formal 继续评分 staging A，同时 manifest 写入源 SHA=B、回执绑定 SHA=B、`verified_same_generation=true`。

复现直接调用生产 `freeze_and_stage`，只在 `_load_producer_yarn_receipt` 调用边界注入一次合法的 B 代两文件提交，不复制或重写 formal 逻辑。关键输出：

### 建议修复与最小重测

不要再分别对“staging 旧快照”和“源目录当前文件”给出同代结论。可采用任一可证明闭合的方案：

1. formal 对每个候选取得与生产者同键的锁，在锁内一次性读取回执 bytes、复制预测到 staging、计算 staging SHA/行数并与该回执比对；或
2. 不依赖锁，但把回执读取成单一 bytes 快照（解析和 receipt SHA 都基于同一 bytes），再把预测复制到 staging，并以 **staging SHA/行数** 对回执声明做校验；源路径之后是否推进不改变已冻结 generation 的身份。

新增真实 barrier 测试：生产者恰在“源复制完成/回执读取前”提交 B。formal 只能（a）拒绝并重试，或（b）发布自洽的 A+A / B+B；不得出现 staging=A、receipt=B 且 `verified=true`。

## 2. `TL-E119-YARN-CORRECTION-SCHEMA-063`

`yarn_receipt.py:555-577` 只验证 sidecar 可解析为 dict、`target_manifest_sha256` 等于目标 manifest 当前 SHA，以及 `correction_version` 是任意非空字符串；`:578-590` 随后无条件生成 `operator_declared_not_effective` 结果。它没有验证：

- `correction_version` 是否为已发布的 `yarn-identity-057-v1`；
- 能确定语义的版本枚举，以及版本 schema 规定的纠偏状态、effective 值与 closure 标志；
- `original_run_identity` 是否与 manifest 中的 `yarn/yarn_factor` 一致；
- `correction.yarn_factor_status/effective_yarn_factor/effective_factor_closed` 是否明确表达 not-effective/null/false。

最小 sidecar 仅含：

```json
{
  "correction_version": "unrecognized-garbage-version",
  "target_manifest_sha256": "<正确目标 SHA>"
}
```

解析仍返回 `effective_yarn_factor=null`、`yarn_factor_provenance=operator_declared_not_effective`。这不是要求抵御恶意写权限，而是防止错误生成/截断/未来未知协议被当前消费者误解释。

建议为纠偏定义严格版本化 schema，并逐位核对关键语义字段；未知版本 fail closed。`target_manifest`、`target_manifest_bytes_unchanged`、`audit_ref` 等元数据可作为诊断信息，不必重复充当安全锚（相邻 sidecar 已由目标字节 SHA 绑定）。新增缺 `correction`、未知版本、原声明 factor 不匹配、`effective_factor_closed=true` 等负例，三份既有完整 sidecar 保持正例。

## 3. `TL-E119-YARN-CONFIG-PARTIAL-064`

`yarn_receipt.py:327-330` 明确允许 `model_config_sha256=None`，而生产者 `pred_ruler.py:268-280` 仅在 `args.model_path/config.json` 是本地文件时计算哈希。`AutoConfig.from_pretrained` 支持模型 ID/缓存解析，这时真实加载的 config 可以存在，但回执仍为 null。

同时 `_validate_common_schema` 把 `generation_params.max_num` 定义为必需并校验类型（`:351-370`），但 `effective_config_sha256` 的 canonical 字段（`:471-487`）只收录 seed/max_gen，漏掉 max_num。复现中 `max_num=1` 和 `max_num=100` 两份回执都合法，且配置 SHA 同为：

```text

```

建议 v2 回执以加载后的 config canonical JSON（例如稳定化 `config.to_dict()`）计算内容哈希，而非只探查本地路径；无法形成 config 身份时应降级 provenance，不能仍称完整闭包。把 `max_num` 纳入指纹，或明确列为自由字段并在对应 task/cell 层绑定它及预期样本集合，避免“必需但不比较”。
